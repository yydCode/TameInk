## 一、问题诊断

### 1.1 四个致命摩擦点

| # | 摩擦点 | 现状代码位置 | 作者的困惑 |
|---|--------|-------------|-----------|
| 1 | **裸 JSON 参数框** | `CreativePage.tsx:30` `json-input` textarea | "我一个写小说的，为什么要填 JSON？" |
| 2 | **候选展示是原始 JSON** | `CreativeWorkspacePage.tsx:317-321` `JSON.stringify` | "这堆花括号是什么意思？" |
| 3 | **"标记 current 故事卡"无 UI** | `creative.py:271-275` 返回 `kind:"input"` → 踢到 `/create` 页 | "什么叫 current？我该点哪里？" |
| 4 | **段落级审批是视觉假象** | `ChapterDraftReview.tsx:139-147` 只写 rationale | "作者以为改了，实际后端存的还是整篇 AI 稿" |

### 1.2 根本原因

系统的内部实现概念（skill、artifact、formal_path、current 指针）**直接暴露给了作者**。后端的严谨性本身是正确的，问题在于前端没有做翻译层。

## 二、核心设计原则

**一句话：作者只做三件事——说想法、看结果、做取舍。其余全部隐藏。**

### 原则一：单一主线

废掉 `/create` 页（手动 skill + JSON 参数框）。作者永远只在工作台，`next_action` 状态机已经知道下一步该做什么，作者只需点"继续"。手动选 skill、填 JSON 参数是系统实现细节，不该存在于 UI。

### 原则二：AI 辅助输入

任何需要作者填的内容，先让 AI 生成草稿，作者修改确认。新建项目、故事卡选择、章节意图，都遵循"AI 先给候选，作者调整"的模式，而不是"空表单等作者填"。

### 原则三：结构化展示，禁止裸 JSON

每种 artifact 类型有专属的可读视图（读者契约 → 契约卡，人物 → 人物卡，期待 → 问题列表）。作者永远看不到花括号。

## 四、工作台设计（主页面）

### 4.1 布局：主轴单栏 + 可收起侧栏

```
┌────────────────────────────────────────────┬──────────────┐
│                                             │              │
│   【当前步骤】 大卡片                        │  期待热力    │
│   ┌──────────────────────────────────┐     │  （折叠态）  │
│   │ AI 建议：现在设计读者契约          │     │              │
│   │                                  │     │  🔴 悬挂 3   │
│   │ [一句话补充你的想法...]           │     │  🟡 进行中 2  │
│   │                                  │     │              │
│   │       [ 让 AI 起草 → ]           │     │  历史 ▸      │
│   └──────────────────────────────────┘     │              │
│                                             │              │
│   ↓ AI 生成后，同一位置变成审阅视图          │              │
│                                             │              │
└────────────────────────────────────────────┴──────────────┘
```

**设计要点**：

- 候选队列不再是常驻左栏。大多数时候只有一个候选在等审阅，直接在主轴展示。多个候选时显示"还有 N 项待处理"提示条。
- 右侧期待热力图默认折叠，用 icon 展开。不占据常驻视觉注意力。
- 历史任务（原 `/review`）收起在右侧抽屉，不是单独页面。

当前 `next_action` banner 已传递正确信息，但视觉层级不够。改为步骤大卡片：

## 七、段落级审批：做真，或诚实

### 现状问题

`ChapterDraftReview` 的段落决策只写进 `decision.rationale` 字符串，后端 `_confirm_artifact` 读的是原始 `payload.markdown`（`creative.py:414-418`）。段落编辑是视觉假象。

### 方案 A：做真（推荐）

后端 `AuthorDecision` 加 `content_override: str | None` 字段。`_confirm_artifact` 对 chapter_draft 优先读 `content_override`：

```python
def _formal_content(kind, payload, decision):
    if kind == "chapter_draft":
        # 优先用作者编辑后的合并版本
        if decision.content_override:
            return decision.content_override
        markdown = payload.get("markdown")
        ...
```

`AuthorDecisionRequest` 加可选字段，前端 `ChapterDraftReview` 在 `onDecide` 时传入 `mergedMarkdown`。改动范围小，但兑现核心承诺。

### 方案 B（临时）

移除段落级 UI，诚实地展示整章审批，说明"接受后你可以在故事库里编辑"。
