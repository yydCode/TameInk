# Tame-Ink 开发落地方案

> 定稿日期：2026-07-21
> 本文档是今日讨论的最终结论，取代此前的规划草稿，作为开发依据。

---

## 一、产品定位（锁定）

**是什么**：番茄网文作者的 AI 创作引擎。作者是主编，AI 是可审计的执行团队。

**核心价值主张**：让有想法但缺经验的作者，写出能通过番茄签约、稳定更新、形成 IP 价值的作品，最终实现月收入过万。

**收入路径**（所有功能围绕这条线）：

```
签约（2万字）→ 全勤奖稳定（3000-4000元/月）
→ 获得推荐位 → 广告收入提升
→ IP 价值形成 → 有声书授权 / 平台迁移 / 改编
→ 月入过万
```

**关键现实约束**（来自平台调研）：
- 番茄是免费+广告模式，纯写作收入天花板约 3000-5000 元/月
- 月入过万必须靠 IP 价值外溢，不能只靠番茄广告分成
- 平台算法 > 写作质量，工具要同时服务"过门槛"和"养 IP"两个目标

---

## 二、体验原则

**系统跟着作者走，而不是作者管理系统。**

- 作者看到的：今天写什么、当前钩子状态、AI 生成的草稿、需要决策的少数关键点
- 系统内部维护的：期待状态机、事实四层隔离、审计链、偏好画像

每个界面的检验标准：**一个正在更新第 30 章的番茄作者，今天会打开这个页面吗？** 答案是"不会"的，不进核心导航。

## 四、技术架构

### 4.1 保留不动

| 模块 | 原因 |
|------|------|
| `domain/creation.py` | 四层隔离、Pydantic 约束、状态机正确 |
| `repositories/artifacts.py` | `BEGIN IMMEDIATE` + 决策审计链正确 |
| `repositories/schema.sql` | 触发器强制约束（FTS 部分除外） |
| FastAPI + SQLite + React | 选型合理 |

### 4.2 必须修复的三个底层问题

**问题一：中文全文搜索质量差**

`schema.sql` 的 FTS5 用 `trigram` 分词器，对中文召回质量极差，直接影响 context 编译质量。

修复：引入 `sqlite-vec` 做向量检索，章节和故事卡存 embedding，按语义召回。同时服务于参考作品的语义检索（一举两得）。

**问题二：两套 agent 系统并存**

旧系统（MarketStrategist 等）+ 新 P0 Skill 系统同时存在，`ChapterPlanner` 在两套里职责不同。

修复：废弃旧系统调用路径，`runtime.py` 的 `AGENT_SKILLS` 旧映射清空，所有任务走 P0 Skill。

**问题三：`P0Skill` 硬编码为 Literal**

每加一个 Skill 要改 5 个文件，平台规则无法写进 Skill 定义。

修复：改为 YAML 驱动，`skills.py` 扫描 `skills/` 目录加载。

### 4.3 Agent 路由重构

```text
任务类型                      执行方式
────────────────────────────────────────────────
确定性操作                    纯 Python（不过 LLM）
（上下文编译、schema 校验）

单次生成类                    直接 LLM 调用 + structured output
（章节草稿、故事卡）          无 agent loop

多步推理类                    DeepAgent loop（现有系统）
（市场调研、多维审稿、卡文诊断）
```

不用 Pi（编程 agent，不相关）。

## 五、知识系统（宝剑侍从教材工程化）

产品差异化的核心：把大神的隐性经验变成系统的显性约束。

### 5.1 Skill YAML 化

每个 Skill 是一个目录：`skill.yaml`（机器可读规则）+ `SKILL.md`（agent 执行说明）。

平台规则直接写进 YAML：

```yaml
name: fanqie-chapter-draft
agent: DraftWriter
candidate_kinds: [chapter_draft]
generation_constraints:
  word_range: [2000, 3500]
  max_paragraph_words: 100
  scene_word_range: [300, 500]
  emotion_beats_per_1000: 1
  telescope_exposures: 3
protagonist_rules:
  must_act_in_setback: true
  setback_cause: external_only
hook_rules:
  near_expectation_max_chapters: 5
  remote_expectation_resurface: true
```

### 5.2 编码来源对照

| 规则 | 来源教材 |
|------|----------|
| 段落≤100字、场景300-500字、每千字1情绪点 | 网文创作理论体系 |
| 抛钩/收钩检测、近期待≤5章 | 期待感——网文的根本 |
| 开篇 18 元素检查 | 开头18元素自助审核 |
| 递望远镜≥3次暴露 | 如何增加爽感期待感 |
| 情绪下行主角必须主动 | 新人扑街主要原因 |
| 七步构思法故事卡骨架 | 七步构思法 |
| 卡文优先级：改剧情>改设定>丢逻辑>不崩人设 | 面对卡文的解决思路 |
| 毒点检测（崩人设/机械降神） | 毒点解析系列 |

### 5.3 内置种子数据

`docs/books/` 的宝剑侍从拆书分析（苟在妖武、大奉打更人、诡秘之主等）作为**内置参考故事卡**，工具首版预装，解决冷启动——上线即有高质量结构模板可借用。

## 六、开发阶段

**Phase 0 — 清场（1周）**
废弃旧 agent 路径；前端非核心页面标 WIP；`P0Skill` 改 YAML 加载；首批平台规则写进 Skill YAML。
验收：`webnovel-draft` 在 YAML 约束下生成，无硬编码 Literal。

**Phase 1 — 核心链路（2-3周）**
端到端：作者描述章节意图 → AI 生成 → 段落级审批 → canon 写入 → 期待账本更新；新审批界面；期待热力图。
验收：从 ReaderContract 到第一章入 canon，全程不超过 6 个页面。

**Phase 2 — 参考作品系统（2周）**
中文搜索修复（sqlite-vec）；参考作品导入 + 拆解；故事卡结构提取；参考故事卡库。
验收：导入一部小说，生成风格基准，能借用其故事卡结构到新项目。

**Phase 3 — 知识诊断（2-3周）**
七步故事卡模板；开篇18元素检查；情绪下行主角被动检测；毒点检测；反复词汇检测。
验收：开篇通过18元素自检≥15项，审稿能检出情绪下行+主角被动。

**Phase 4 — 番茄平台适配（2周）**
签约节点感知；全勤奖倒计时；类型专项规则 YAML；IP 健康度指标；书名简介生成整合。
验收：一眼看到"距签约还差X字"和"今天需更新Y字拿全勤"。

## 七、不做的事

- ❌ 强制全书前置大纲（可作为**可选参考**导入，但不作硬框架）
- ❌ 短剧功能（P3 再做）
- ❌ 自动静默写入 canon
- ❌ 随机灵感生成 / 套路拼剧情
- ❌ Skill 社区市场（当前阶段）
- ❌ 多用户 / 云端（本地优先）
- ❌ Pi agent 框架（编程工具，不相关）

---

## 八、关于"越用越聪明"

不靠训练模型，靠两个机制：

1. **参考风格对齐**：导入参考作品 → 拆解风格基准 → 生成时注入 context
2. **作者偏好积累**：记录段落接受/拒绝/修改历史 → 形成偏好画像 → 注入 context

RAG + 偏好注入即可实现，效果快速可感知。LoRA 微调（平台级学习）留到有用户规模后。

**技术亮点**：

- jieba 分词在模块级初始化，避免每次查询重复加载词典（~0.5s 延迟）
- FTS5 存储 jieba 分词后的空格分隔文本，用 unicode61 tokenizer 匹配
- SearchRepository 的 `_excerpt` 方法从原文件读取内容做精确匹配，过滤 FTS 假阳性
- 毒点清单来源于宝剑侍从《毒点解析》系列教材，覆盖读者弃书的 9 大结构性陷阱
